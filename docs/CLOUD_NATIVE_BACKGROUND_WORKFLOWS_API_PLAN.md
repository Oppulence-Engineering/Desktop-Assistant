# Execution Plan: Cloud-Native Background Workflows — API (rowboat-api)

> Companion to [CLOUD_NATIVE_BACKGROUND_WORKFLOWS_RFC.md](./CLOUD_NATIVE_BACKGROUND_WORKFLOWS_RFC.md).
> Scope: **only the Go backend (`apps/rowboat-api`) work** for the gaps the RFC
> marks 🟡/⬜. Desktop/renderer work (the global Cloud Runs view UI, sync-state
> indicator, rerun button) is **out of scope here** — but the API changes this plan
> makes are what those UI features will consume.
>
> **Status: implemented.** WP1–WP8 below are done. `make generate` + `make test`
> (incl. `-race`) pass; `helm lint`/`template` pass with the new worker
> Service/ServiceMonitor. Decisions taken: **Temporal Cloud uses API-key auth**;
> **error-code taxonomy is granular** (`internal/backgroundtaskworkflow/errcodes.go`).
> Remaining (explicitly out of API scope): the desktop UI surfaces and the kind
> E2E extension for cancel/retry/failure/desktop-closed (Go-level tests cover
> these paths). Staging/prod Temporal Cloud is wired but gated `TEMPORAL_ENABLED:
> "false"` until the namespace + API key are provisioned.

## Context

The cloud path is implemented and validated in kind, but the API still has the gaps
in RFC §6: inconsistent run vocabulary/lineage, missing run/artifact fields, **no
cloud-run observability**, **no Temporal Cloud auth** (so staging/prod can't run it),
and happy-path-only tests. This plan turns those gaps into ordered, code-referenced
work packages with exact insertion points, the required codegen/migration steps, and
per-package verification.

### Decisions to confirm before/while executing

These shape the implementation; recommended defaults in **bold** so work can start.

1. **Status term:** the API **already uses `stopped`** everywhere
   (`handler.go:835`, `ent/schema/background_task_run.go:38`,
   `packages/shared/src/background-task.ts:28`). The "cancelled" drift lived only in
   prose. **Keep `stopped`** (no migration); only docs/UI labels change. → No API code
   change required for this item.
2. **Retry lineage:** keep `previous_run_id` for ordering and **add a dedicated
   `retry_of_run_id`** (recommended) vs. overloading the existing field.
3. **Audit storage:** **reuse the append-only `BackgroundTaskRunEvent` stream** with
   `audit.*` event types (recommended for v1) vs. a separate audit table.
4. **Temporal Cloud auth:** **API-key static credentials** (simplest) vs. mTLS client
   certs. Affects which secrets/env vars we standardize ([WP6](#wp6--temporal-cloud-connection)).
5. **Error taxonomy:** the set of `error_code` values. A small starting enum is
   proposed in [WP2](#wp2--structured-errors--lineage-fields); confirm the list.

## Conventions (apply to every schema-touching package)

Every package that edits `apps/rowboat-api/ent/schema/*` must, in one commit:

1. Edit the schema file.
2. Run `make generate` (from `apps/rowboat-api/`) — reruns ent + enthistory + entoas +
   OpenAPI + entgql; **CI fails on drift**, so never hand-edit generated files.
3. Update handler/view/validation code that reads or writes the new field.
4. `make test` (`go test ./... -race -count=1`).

All new run columns are **additive and nullable/defaulted**, so `AUTO_MIGRATE`
(on in kind/staging) applies them safely; production (`AUTO_MIGRATE=false`) picks them
up via the normal migration step. Adding an enum *value* (e.g. `retry`) is only a
validator change — the columns are plain `string`, so **no DB migration** for that.

## WP1 — Retry as a first-class trigger + lineage

**Goal:** retries are visibly retries with unambiguous lineage (RFC §6.1.2).

**Schema** — `ent/schema/background_task_run.go`
- Add `retry` to the trigger validator (line 35):
  `oneOfBackgroundTask("trigger", "manual", "cron", "window", "event", "retry")`.
- Add field `field.String("retry_of_run_id").Optional()` (next to `previous_run_id`,
  line 46).

**Handler** — `internal/backgroundtasks/handler.go`
- `validateRunTrigger` (line 1719): add `retry` to the accepted set.
- `createRunRequest` struct (line 178): add `RetryOfRunID string json:"retryOfRunId"`.
- `applyTemporalCreateFields` (line 1575): set `retry_of_run_id` when present.
- `startRetryRun` (line 1113): change `Trigger: previous.Trigger` →
  `Trigger: "retry"`, add `RetryOfRunID: previous.RunID`; pass `Trigger: "retry"`
  into the `StartInput` (line 1142). Keep `PreviousRunID: previous.RunID` for ordering.
- `viewRun`/`runView` (line 1354): add `RetryOfRunID` to the JSON view.

**OpenAPI** — regenerated by `make generate`; confirm `enrich.go:264-293`
(`BackgroundTaskRun` schema) shows the new field; add a one-liner if the enricher
needs it.

**Verify:** unit test in `handler_test.go` — POST `.../retry` on a failed run yields a
new run with `trigger=retry`, `retryOfRunId=<original>`, original untouched.

## WP2 — Structured errors + lineage fields

**Goal:** add `attempt`, `cancel_requested_at`, `error_code`, `error_details` and
populate them (RFC §6.1.3).

**Schema** — `ent/schema/background_task_run.go`, add:
- `field.Int("attempt").Default(1).Positive()`
- `field.Time("cancel_requested_at").Optional().Nillable()`
- `field.String("error_code").Optional()`
- `field.Text("error_details").Optional()`

**Error taxonomy** — new `internal/backgroundtasks/errors.go` with a small enum
(confirm in Decision 5):
`temporal_start_failed | temporal_cancel_failed | activity_failed | task_inactive | timeout | internal`.
A helper `classifyRunError(err) (code, details string)` keeps mapping in one place.

**Population points:**
- `attempt`: default 1 in `createRun`; in `startRetryRun` set
  `attempt = previous.Attempt + 1`.
- `cancel_requested_at`: set in `CancelRun` (handler.go:832) alongside the existing
  `stopped` update.
- `error_code` / `error_details`: set where `SetError(...)` is called today —
  `triggerAPIRun` start-failure (line 1084), `startRetryRun` start-failure (line 1147),
  and the worker's `MarkRunFailed` activity (`workflow.go:315`).

**Views** — add the four fields to `viewRun` (1354) and `error_code`/`error_details`
to `viewRunStatus` (1387).

**Verify:** tests asserting cancel sets `cancelRequestedAt` + `stopped`; a forced
activity failure sets `errorCode`/`errorDetails`; retry increments `attempt`.

## WP3 — Artifact provenance

**Goal:** know which run wrote an artifact, and its media type (RFC §6.1.4).

**Schema** — `ent/schema/background_task_artifact.go`, add:
- `field.String("updated_by_run_id").Optional()`
- `field.String("content_type").Default("text/markdown")`

**Worker** — `internal/backgroundtaskworkflow/workflow.go`, `upsertArtifact`
(line 353): accept the run id (it's in `StartInput.RunID`) and set
`updated_by_run_id`; set `content_type` (default markdown).

**Handler** — `PutArtifact` (handler.go:542) accepts optional `contentType`; artifact
views include both fields. Artifact history retention is deferred to the open question
in the RFC.

**Verify:** after a worker run, `GET .../artifact` returns `updatedByRunId` =
producing run and `contentType`.

## WP4 — Canonical event vocabulary + queued event

**Goal:** a documented, validated event set (RFC §6.1.5).

- New `internal/backgroundtaskworkflow/events.go` (or a shared constants block)
  defining the canonical types:
  `temporal.queued, temporal.running, temporal.progress, temporal.artifact_updated,
  temporal.completed, temporal.failed, temporal.cancel_requested, temporal.stopped,
  temporal.signal, temporal.retry_requested`.
- Emit `temporal.queued` at trigger time in `triggerAPIRun` (line 1052) — today a
  queued run has no event. Emit `temporal.retry_requested` in `startRetryRun`. Emit a
  terminal `temporal.stopped` in `CancelRun` once cancellation is confirmed (distinct
  from `cancel_requested`).
- `AppendRunEvents` (handler.go:913) keeps accepting arbitrary types for
  forward-compat but **logs a warning** on unknown types (don't hard-reject).

**Verify:** event timeline of a normal run begins with `temporal.queued`; cancel path
shows `cancel_requested` then `stopped`.

## WP5 — Observability (metrics, structured logs, audit, tracing)

**Goal:** answer "what ran, who, how long it waited, where, why it failed, what it
produced" from telemetry (RFC §6.2). This is the largest package.

### 5a. Metrics
New `internal/backgroundtasks/metrics.go` using `promauto` (mirror the style of
`internal/db/metrics.go`). Package-level vars so **both the API and worker processes
register the same series**:

- Counters: `cloud_runs_triggered_total{trigger}`, `cloud_runs_completed_total`,
  `cloud_runs_failed_total`, `cloud_runs_stopped_total`, `cloud_run_retry_total`,
  `cloud_run_cancel_requested_total`, `cloud_run_artifact_sync_failures_total`.
- Histograms: `cloud_run_duration_seconds`, `cloud_run_queue_latency_seconds`.
- **Cardinality rule:** label only by low-cardinality dims (`trigger`, `executor`).
  Never label by `runId`/`userId`.

Emit from:
- API: `triggerAPIRun` (triggered), `CancelRun` (cancel_requested + stopped),
  `startRetryRun` (retry + triggered).
- Worker activities (`workflow.go`): `MarkRunRunning` computes queue latency
  (`started_at − created_at`); `MarkRunDone` (completed + duration);
  `MarkRunFailed` (failed); `upsertArtifact` failure (artifact_sync_failures).

> **Required sub-step:** the **worker has no `/metrics` endpoint** today. Add a small
> `promhttp` server to `cmd/worker/main.go` (reuse the pattern at
> `internal/server/server.go:115`) bound to the metrics port, so completion/failure/
> duration series are scrapeable. The chart's worker deployment must expose + scrape
> that port (chart change, tracked with the deployment work).

### 5b. Structured lifecycle logging
Helper `runLogFields(ctx, run) []zap.Field` returning the consistent set:
`runId, taskSlug, userId, workflowId, temporalRunId, traceId, trigger, status`
(`traceId` from the active OTel span — tracing is already initialized in the worker via
`telemetry.InitTracer`, `worker/main.go:50`). Replace ad-hoc `h.log.Error(...)` at each
lifecycle transition (trigger/cancel/retry in the handler; the four activities) with
`h.log.Info("bg run <event>", runLogFields(...)...)`.

### 5c. Audit events
Per Decision 3 (recommended: reuse the event stream): emit `audit.*` events via the
existing `appendSystemEvent`/`appendEvent` helpers for: trigger requested, worker
claimed, artifact updated, completed, failed, cancel requested, stopped, retry
requested. (Artifact-*pulled* is a desktop action — out of scope here.)

### 5d. Tracing
Wrap the trigger handler and each activity in a span (`trigger.bg_run`,
`activity.<name>`) and attach `runId`/`taskSlug` attributes so the `traceId` in 5b is
meaningful and cross-process traces link the API trigger to the worker activities.

**Verify:** `make test`; in kind, `curl :metrics` on both API and worker shows the new
series after a run; logs show the full field set; the event stream shows `audit.*`.

## WP6 — Temporal Cloud connection

**Goal:** let staging/production connect to **Temporal Cloud** (RFC §6.4). Currently
`Dial` (`workflow.go:85`) sets only `HostPort` + `Namespace` — no TLS/auth.

**Config** — `internal/appconfig/config.go`
- Add fields (struct ~line 136; `Load` ~line 224): `TemporalAPIKey`,
  `TemporalTLSCert`, `TemporalTLSKey`, `TemporalTLSCA`, `TemporalTLSEnabled`.
- `Validate` (line 244): when `TemporalEnabled` and targeting Cloud, require either
  `TemporalAPIKey` **or** (`TemporalTLSCert` + `TemporalTLSKey`).

**Dial** — `internal/backgroundtaskworkflow/workflow.go:85`
- Build `client.Options.ConnectionOptions.TLS` from the cert/key (mTLS) **or** set API
  -key credentials (`client.NewAPIKeyStaticCredentials`), per Decision 4. Because both
  the server (`wire.go:102`) and worker (`worker/main.go:80`) call `Dial`, this single
  change enables Cloud for both processes.

**Deployment companion** (charts — note here, execute alongside): set
`TEMPORAL_ENABLED: "true"`, the Cloud gRPC `TEMPORAL_ADDRESS`, the Cloud namespace, and
the new auth env vars sourced from `rowboat-api-secrets`/Infisical in
`values-staging.yaml` then `values-production.yaml`; enable the worker deployment.
**Never inline secrets in values.**

**Verify:** locally, a unit test that `Dial` builds TLS/credentials options when the
fields are set (no live Cloud needed). End-to-end validation happens when staging is
pointed at a real Temporal Cloud namespace.

## WP7 — Run-list filters (API support for the global Cloud Runs view)

**Goal:** back the renderer's future global view (RFC §6.3) with server-side filtering.

**Handler** — `ListAllRuns` (handler.go:636) and `ListRuns` (line 606): accept query

**OpenAPI** — document the new query params (regenerate; adjust `enrich.go` if needed).

**Verify:** tests for each filter dimension and a combined query; assert pagination
still works.

## WP8 — Test coverage (cancel / retry / failure / desktop-closed)

**Goal:** exercise the non-happy paths (RFC §6.5).

- **Go unit/integration** (`internal/backgroundtasks/handler_test.go`, new
  `workflow_test.go`): cancel running → `stopped` + `cancel_requested_at`; retry failed
  → linked run with `trigger=retry`, `attempt+1`; forced activity failure →
  `error_code`/`error_details`; list filters.
- **kind E2E** (`scripts/rowboat-api-kind.sh`): extend
  `validate_temporal_background_task` (line 390) — add a cancel scenario (trigger a
  long run, cancel, assert `stopped`), a retry scenario (assert linked successful
  retry), and assert the new fields/metrics appear. Wire into `validate-full`.

**Verify:** `make test`; `scripts/rowboat-api-kind.sh up` then the extended validators
pass.

## Global verification

- `cd apps/rowboat-api && make generate` → **no git diff** in generated files
  (CI gate). Then `make test` (race).
- `make helm-validate` (chart lint/template) if charts touched in WP6.
- `scripts/rowboat-api-kind.sh up` → extended smoke (WP8) green: create → trigger →
  succeed → **cancel** → **retry** → events → artifact, with new fields populated and

- Sanity-curl `:9090/metrics` (API) and the worker metrics port for the
  `cloud_runs_*` / `cloud_run_*` series.

## Risks & notes

- **Generated-file drift** is the most common breakage: always commit schema + `make
  generate` output together.
- **Metric cardinality:** keep labels low-cardinality; the run id belongs in
  logs/traces, not labels.
- **Worker metrics endpoint** is net-new infra (5a) — don't forget the chart port +
  ServiceMonitor target.
- **Temporal Cloud auth** is the only item needing real external credentials; everything
  else is verifiable locally in kind.
- Keep `previous_run_id` for backward compatibility even after adding
  `retry_of_run_id` (desktop types/UI already read `previousRunId`).
